# 系统架构设计

> 文档状态：商业版目标架构草案  
> 当前实现：单机 Gradio + Python 进程  
> 最近更新：2026-09-02

## 1. 架构目标

- 将Web请求与耗时GPU推理解耦。
- 保证任务可排队、可恢复、可取消、可审计。
- 一张GPU默认只运行一个模型工作进程，避免不可控并发导致OOM。
- 模型常驻显存，任务间复用。
- 输入、输出、元数据和日志分离存储。
- 支持从单GPU平滑扩展到多GPU。

## 2. 当前架构

```text
浏览器
  │ 上传视频
  ▼
Gradio进程
  ├─ OpenCV读取视频
  ├─ Transformers加载模型
  ├─ CPU或GPU逐帧推理
  ├─ OpenCV写入MP4
  └─ 可选FFmpeg复制音频
```

### 当前优点

- 结构简单，便于验证算法。
- 视频和模型均在本机处理。
- `_model_cache` 可以在同一进程内复用模型。
- 已有逐帧进度和时间平滑。

### 当前不足

- Web请求与推理位于同一进程。
- 页面刷新后无法恢复任务。
- 没有持久化队列和任务记录。
- 单帧串行推理，GPU利用率不足。
- 异常没有分类，用户只会看到通用错误。
- 临时目录没有统一生命周期管理。
- 多进程会重复加载模型并占用显存。

## 4. 组件职责

### 4.1 Web前端

- 登录、套餐和额度展示。
- 分片上传与断点续传。
- 参数配置、任务列表和结果下载。
- 通过SSE或WebSocket显示进度；连接失败时降级为轮询。
- 不直接持有对象存储永久凭证。

### 4.2 FastAPI API

- 鉴权和租户隔离。
- 生成短期上传、下载凭证。
- 视频元数据预检。
- 创建任务、预占额度和生成幂等键。
- 查询、取消和删除任务。
- 不在API进程内执行深度模型。

### 4.3 PostgreSQL

- 用户、套餐、额度流水和订单。
- 任务主记录和不可变状态事件。
- 文件生命周期与删除状态。
- 支付回调幂等记录。

PostgreSQL是业务事实来源；Redis不能作为唯一任务记录。

### 4.4 Redis与Celery

- 任务排队和路由。
- 短期进度、心跳和排队位置缓存。
- 可重试错误的延迟重试。
- GPU类型、模型和优先级队列分流。

### 4.5 GPU Worker

- 启动时加载并预热模型。
- 从对象存储下载输入到任务工作目录。
- 解码、批量推理、平滑和编码。
- 定期更新进度与心跳。
- 输出校验成功后上传结果。
- 清理工作目录和释放临时张量。

每个GPU默认一个工作进程，Celery并发设为1；并行度主要来自帧批处理，而不是在同一GPU上同时运行多个视频任务。

### 4.6 对象存储

- Bucket默认私有。
- 输入与输出使用不同前缀和生命周期规则。
- 下载使用短期签名URL。
- 文件键使用内部UUID，不采用用户原始路径。

## 5. GPU推理设计

### 5.1 基本策略

- `model.eval()` 与 `torch.inference_mode()` 同时使用。
- CUDA上使用 `torch.autocast(device_type="cuda", dtype=torch.float16)`。
- 输入帧按批次传给处理器；批量大小通过启动配置和显存探测确定。
- 使用固定模型实例，不在每个任务中重新加载。
- 将解码、预处理、GPU推理和编码设计为有界流水线。

### 5.2 建议流水线

```text
解码线程
  → 有界帧队列
  → CPU预处理/批组装
  → GPU批量推理
  → 深度归一化与时间平滑
  → 编码线程
```

队列必须有上限，防止长视频把全部内存占满。

### 5.3 显存不足处理

1. 记录模型、分辨率、批量和空闲显存。
2. 清理当前任务张量。
3. 批量大小减半后最多重试一次。
4. 仍失败则返回 `GPU_OOM`，建议用户降低分辨率。
5. 不得对确定性OOM无限重试。

### 5.4 模型策略

- v1仅开放Small模型，减少显存、成本和许可证复杂度。
- Base和Large必须在完成性能、成本和许可证审查后开放。
- 模型版本必须固定到不可变版本或提交哈希。
- 升级模型需要离线回归和灰度发布。

## 6. 任务状态机

```text
CREATED
  → UPLOADING
  → VALIDATING
  → QUEUED
  → RUNNING
  → ENCODING
  → UPLOADING_RESULT
  → SUCCEEDED
```

异常和人工操作分支：

```text
VALIDATING → REJECTED
QUEUED/RUNNING → CANCEL_REQUESTED → CANCELLED
RUNNING/ENCODING → RETRY_WAIT → QUEUED
任意运行阶段 → FAILED
SUCCEEDED/FAILED/CANCELLED → EXPIRED → DELETED
```

状态只能沿允许的边转换；每次转换写入独立事件记录。

### Job

- `status`
- `model_name`、`model_revision`

### JobEvent

- `event_type`
- `from_status`、`to_status`

- `worker_id`

### UsageLedger

- `idempotency_key`
- `created_at`

## 8. 一致性与幂等

- 创建任务要求 `Idempotency-Key`。
- 同一用户、同一键、同一请求内容只创建一个任务。
- 任务重试复用原 `job_id`，不重复预占额度。
- 输出文件先写临时键，校验后再写最终键并提交数据库事务。
- 删除操作可重复执行；目标已不存在时仍返回成功。
- 支付回调按支付平台事件ID去重。

## 9. 进度设计

建议阶段权重：

| 阶段 | 百分比 |
|---|---:|
| 预检 | 0–5 |
| 准备模型 | 5–10 |
| 深度推理 | 10–85 |
| 编码 | 85–95 |
| 上传与校验 | 95–100 |

GPU Worker每处理若干帧或每1秒更新一次Redis，数据库只在阶段变化和关键里程碑落库，避免写入放大。

## 10. 扩展策略

### 单GPU

- 一个GPU队列。
- 一个常驻Worker。
- 并发1，内部批处理。

### 多GPU

- 每张GPU一个Worker实例。
- 按模型、GPU等级和任务优先级路由。
- 调度前读取可用显存和Worker心跳。
- 不把已运行任务迁移到另一GPU；失败后重新入队。

### 自动扩缩容

- 扩容信号：队列等待时间、队列长度和预计处理分钟数。
- 缩容前停止接新任务，并等待当前任务完成或安全取消。
- 模型预热完成前实例不进入可用池。

## 11. 可观测性

### 指标

- 队列长度和P50/P95等待时间。
- 每分钟视频的处理秒数。
- GPU利用率、显存、温度和OOM次数。
- 各阶段耗时。
- 成功率、重试率、取消率和错误码分布。
- 单任务与单视频分钟成本。

### 日志

- 使用结构化JSON日志。
- 每条日志包含 `job_id`、`worker_id` 和 `attempt`。
- 不记录访问令牌、支付信息、视频二进制或用户完整文件名。
- 后台保存详细堆栈；前端仅显示公共错误。

## 12. 关键架构决策

| 决策 | 选择 | 原因 |
|---|---|---|
| Web框架 | FastAPI | 适合异步API、类型模型和OpenAPI |
| 任务系统 | Celery + Redis | 具备成熟的重试、路由和Worker生态 |
| 业务数据库 | PostgreSQL | 需要任务、计费和审计一致性 |
| 文件存储 | S3兼容对象存储 | 便于私有访问、生命周期和扩展 |
| 原型UI | Gradio | 继续用于内部验证，不直接承担公网商业入口 |
| GPU并发 | 每GPU一个任务 | 降低OOM和资源争抢，内部用帧批处理提速 |

以上选择在MVP阶段有效；达到高并发后再评估专用推理服务或其他任务平台，不提前增加复杂度。
