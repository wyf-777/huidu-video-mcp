# 部署与运维手册

> 文档状态：商业版目标方案；当前仓库尚未包含下述容器和服务配置  
> 适用对象：开发、测试、运维和值班人员  
> 最近更新：2026-09-02

## 1. 部署原则

- 本地 Gradio 原型只用于算法验证和内部使用，不直接暴露到公网。
- API、任务队列、GPU推理和文件存储相互解耦。
- PostgreSQL是任务、订单和额度的业务事实来源；Redis只保存队列和短期状态。
- 输入、输出均存入私有对象存储，通过短期签名地址访问。
- 每张GPU默认启动一个推理Worker，每个Worker同时执行一个视频任务。
- 镜像、模型、数据库迁移和配置均需版本化，生产发布必须可回滚。

## 2. 环境划分

| 环境 | 用途 | 数据 | GPU | 对外访问 |
|---|---|---|---|---|
| 本地 | 开发和单元测试 | 合成或脱敏数据 | 可选 | 否 |
| 测试 | 集成、回归和压测 | 专用测试数据 | 至少一张兼容GPU | 仅团队/VPN |
| 生产 | 付费用户服务 | 用户真实数据 | 独立GPU节点 | HTTPS |

三个环境使用不同数据库、Redis实例、对象存储桶、域名和密钥。禁止从生产复制原始用户视频到测试环境。

## 3. 生产组件

最小可用生产部署包含：

- Web前端与CDN；
- HTTPS反向代理或云负载均衡；
- FastAPI API服务，至少两个副本；
- PostgreSQL，启用自动备份和时间点恢复；
- Redis，用于Celery broker、锁和短期进度；
- Celery GPU Worker，每张GPU一个进程；
- Celery轻量Worker，用于探测、转码后处理、通知和清理；
- S3兼容私有对象存储；
- FFmpeg和ffprobe；
- 集中日志、指标、错误追踪和告警系统。

单机MVP可以把上述组件部署在少量主机上，但进程、数据目录和凭证仍需隔离。

## 4. 容器与GPU基线

生产Linux主机应安装：

1. NVIDIA驱动；
2. Docker Engine；
3. NVIDIA Container Toolkit；
4. 与驱动兼容的CUDA版PyTorch镜像或固定基础镜像。

GPU容器验证：

```bash
nvidia-smi
docker run --rm --gpus all nvidia/cuda:12.6.3-base-ubuntu24.04 nvidia-smi
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

具体CUDA、PyTorch和驱动版本必须在构建时根据官方兼容矩阵重新确认。不要以开发机上的CPU依赖锁定生产GPU镜像。

镜像要求：

- 固定基础镜像摘要和Python依赖版本；
- 固定FFmpeg版本；
- 以非root用户运行API和Worker；
- 不在镜像中保存密码、访问密钥或用户视频；
- 构建后执行依赖漏洞扫描和软件物料清单（SBOM）导出；
- 模型权重在镜像、只读共享卷或受控缓存中固定版本和校验值。

## 6. 发布流程

### 6.1 发布前门禁

- 目标提交已通过代码审查。
- `TEST_PLAN.md` 中P0/P1测试全部通过。
- 数据库迁移已在测试环境演练升级和回滚。
- 镜像、模型revision和SBOM已归档。
- 许可证与安全扫描无未接受的高危问题。
- GPU短视频冒烟测试通过，输出可被ffprobe和主流浏览器识别。
- 对象存储生命周期、备份和告警已验证。

### 6.2 推荐发布顺序

1. 备份数据库并记录当前版本。
2. 执行向后兼容的数据库迁移。
3. 发布API灰度副本，运行健康检查。
4. 暂停新GPU任务派发，让旧Worker排空。
5. 逐台替换Worker并执行模型预热。
6. 恢复队列，观察错误率、排队时长和显存。
7. 扩大流量，记录发布人、版本和时间。

数据库变化采用“先扩展、后迁移、再收缩”，避免旧代码和新结构不能共存。

## 7. 回滚

满足任一条件应停止发布或回滚：

- 5分钟窗口任务失败率超过5%；
- API 5xx显著高于发布前基线；
- 出现跨用户文件访问或计费错误；
- GPU持续OOM或Worker反复退出；
- 输出视频出现系统性损坏。

回滚步骤：停止新任务派发，恢复上一版API和Worker镜像，确认旧版本兼容数据库，重新排队未开始任务。已扣费但失败的任务必须自动退回额度。涉及数据泄露时，不以普通回滚结案，应立即进入安全事件流程。

## 8. 健康检查与监控

### 8.1 健康检查

- `/health/live`：进程存活，不访问外部依赖；
- `/health/ready`：数据库、Redis和必要配置可用；
- Worker心跳：最近心跳、当前任务和模型版本；
- GPU检查：驱动可见、显存余量和温度正常；
- 对象存储：使用专用探针桶验证读写，不触碰用户文件。

### 8.2 核心指标

| 类别 | 指标 |
|---|---|
| API | 请求量、P50/P95/P99延迟、4xx、5xx |
| 队列 | 等待任务数、最老任务等待时间、任务吞吐 |
| 推理 | 每帧耗时、每分钟视频处理耗时、批大小、OOM次数 |
| GPU | 利用率、显存、温度、功耗、ECC错误（如支持） |
| 任务 | 成功率、失败率、取消率、重试次数、各状态停留时间 |
| 视频 | 上传/下载失败、探测失败、转码失败、输出损坏 |
| 计费 | 预占失败、结算差异、回调重复、退款异常 |
| 存储 | 容量、临时文件年龄、生命周期删除失败 |

日志必须使用结构化JSON，并至少包含：`timestamp`、`level`、`service`、`request_id`、`job_id`、`user_id_hash`、`event`、`error_code`、`duration_ms`。不得记录原始令牌、支付信息、签名URL或视频内容。

## 9. 告警建议

| 严重度 | 示例 | 响应目标 |
|---|---|---|
| P0 | 跨租户访问、密钥泄露、错误扣费扩大 | 立即停止相关入口，15分钟内响应 |
| P1 | 全站不可用、队列不消费、持续GPU OOM | 15分钟内响应 |
| P2 | 单Worker故障、失败率升高、存储逼近阈值 | 工作时间1小时内响应 |
| P3 | 性能趋势恶化、非关键清理失败 | 下一工作日处理 |

告警必须包含环境、版本、指标、开始时间、影响范围和运行手册链接，避免只发送“服务异常”。

## 10. 任务失败、重试与恢复

- 网络超时、对象存储短暂失败和GPU节点临时不可用可以指数退避重试。
- 输入损坏、不支持编码、参数非法和明确OOM不得无条件重试。
- 每个任务建议最多自动执行3次；重试必须使用同一业务任务ID和独立尝试ID。
- Worker失联后，只有租约超时且确认没有活跃进程才能重新派发。
- 每次输出写入临时对象，校验成功后原子标记为最终结果。
- 取消采用协作式检查，至少在解码批次、推理批次和编码阶段检查取消标记。

## 11. 备份与恢复

| 数据 | 策略 | 建议目标 |
|---|---|---|
| PostgreSQL | 每日全量 + 持续WAL/PITR | RPO ≤ 15分钟，RTO ≤ 2小时 |
| Redis | 可重建，不保存唯一业务事实 | RPO不作业务承诺 |
| 输入/输出 | 对象版本和生命周期按产品政策 | 误删恢复仅在保留期内 |
| 配置/镜像 | Git、镜像仓库、制品签名 | 可恢复任一生产版本 |
| 审计日志 | 独立只追加存储 | 依法定/合同周期保存 |

至少每季度进行一次恢复演练。备份成功不等于可恢复，演练需记录耗时、数据完整性和失败项。

## 12. 容量规划

上线前用目标GPU测量不同分辨率、帧率、时长和模型的实时倍率：

```text
实时倍率 RTF = 总处理秒数 / 输入视频秒数
单GPU小时产能 = 3600 / RTF 个视频分钟
所需GPU数 ≈ 峰值每小时视频分钟 × RTF / 3600 / 目标利用率
```

目标利用率建议不高于70%，为波峰、重试和维护预留余量。扩容同时参考最老任务等待时间，而不是只看GPU利用率。

## 13. 常见故障运行手册

### 队列增长但GPU空闲

检查Worker心跳、队列路由、Redis连接、任务租约和模型预热状态。确认后重新启动单个Worker，禁止同时清空队列和数据库任务记录。

### GPU OOM

停止派发到故障Worker，记录输入规格和批大小，清理进程后降低批大小重试一次。持续OOM应标记为资源不足并退回额度，不应无限重试。

### 输出无法播放

保留失败产物的内部诊断副本，运行ffprobe检查时长、流、像素格式和moov atom；重新转码成功后再发布。诊断副本也受保留期约束。

### 对象存储不可用

暂停新上传和任务启动，已在GPU执行的任务可完成到本地受控临时区，但不得报告成功，直到结果持久化并校验。

## 14. 下线与数据清理

服务下线前停止新订单和新任务，等待或取消在途任务，导出应保存的账务与审计记录，执行用户数据删除策略，吊销密钥并关闭公网入口。删除完成后保留一份不含用户媒体的下线审计报告。
